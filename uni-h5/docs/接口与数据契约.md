### 1.4 瀑布流选型结论

**选原生 `scroll-view` 双列瀑布流，不引虚拟列表。** 依据：

- 首页数据源单次返回量可控（`/user/home/feed` 一次给全量 feed，非无限分页流），DOM 规模在**几十到一两百个卡片**量级，远低于虚拟列表的收益阈值（通常需要 1000+ 节点才明显）。
- 虚拟列表在 uni-app H5 端存在**已知的滚动位置错乱与图片复用闪烁**问题，卡牌类商品卡片高度不一（封面比例 + 标题两行 + 价格行），动态高度虚拟列表实现复杂度和 bug 风险显著高于收益。
- 原生方案在 H5 端可直接复用浏览器原生滚动与 `IntersectionObserver` 懒加载，首屏性能足够。
- **留出升级口**：把瀑布流封装为独立组件 `<waterfall-list>`，对外只暴露 `list` / `@load-more`；后续若商品量级上来，替换内部实现为虚拟列表**不改调用方**。

**触发升级的信号**：单次渲染卡片数稳定超过 500，或中低端安卓机首屏滚动出现可感知掉帧。

## 三、接口明细

### 3.1 ✅ 直接复用（现状即满足）

#### ① GET `/user/blindbox/detail`

- **鉴权**：无（公开，游客可浏览）
- **Query**：`id` int，**必填**（缺失 / 非法 / ≤0 → 400）

**响应 200（裸 JSON，非信封）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `blind_box` | object | 盲盒主体（`mall_blind_boxes` 模型） |
| `supplier` | object | **白名单投影**：`{id, name, logo, bio}` |
| `pool` | object | 卡池（`mall_card_pools`） |
| `items` | array | 卡池条目 `mall_card_pool_items[]`，含 `rarity` / `weight` / `stock` |
| `pool_total_stock` | int64 | 卡池剩余总库存 |
| `active_promotion` | object\|null | 生效中的促销（`omitempty`） |
| `effective_price` | float64 | **前端应展示的价格**（活动价优先，回退原价） |
| `cached_at` | time | 缓存时间戳 |

**错误**：`400 blindbox.invalid_id` / `404 blindbox.not_found` / `500 blindbox.internal`

> **H5 对接要点**：概率公示表直接用 `items[]` 的 `weight / 10000` 换算为百分比；库存进度条用 `pool_total_stock`。

---

#### ② POST `/user/blindbox/draw`

- **鉴权**：`Authorization: Bearer <token>`（中间件 `UserAuth()`）
- **限流**：`RateLimitPerMinute("draw:{uid}", 30)` → 同 uid 同分钟第 31 次返回 **429**
- **请求体**：`{ blind_box_id: int64 }`，**必填**

**响应 200（裸 JSON）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `order_id` | int64 | 订单 ID |
| `order_no` | string | 订单号（32 位） |
| `actual_price` | float64 | **实付价**（可能因活动价低于展示价） |
| `cards` | array | 抽中的卡，空时返回 `[]` 而非 `null` |
| `cards[].item_id` | int64 | 卡池条目 ID |
| `cards[].card_id` | int64 | 卡牌 ID |
| `cards[].rarity` | string | `SSR` / `SR` / `R` / `N` —— **四档，前端边框配色依据** |
| `cards[].snapshot_name` | string | 快照名（下单时冻结，不随卡牌改名） |
| `cards[].snapshot_image` | string | 快照图 |

**错误码全集（`mapDrawErr`）**

| HTTP | code | 前端处理 |
|---|---|---|
| 400 | `draw.invalid_input` | 埋点上报，提示「参数异常」 |
| 401 | `draw.unauthorized` | **跳登录页并带 `redirect` 回跳** |
| 402 | `draw.insufficient_balance` | 弹「余额不足」，引导到「我的」 |
| 403 | `draw.user_not_available` | 提示账号不可用，退回首页 |
| 404 | `draw.blindbox_not_available` | 提示商品已下架，返回首页并刷新 |
| 409 | `draw.sold_out` | 提示已售罄，**自动刷新详情页库存** |
| 429 | `rate_limited` | 提示「操作过于频繁」，**按钮禁用 3 秒** |
| 500 | `draw.internal` | 通用失败，允许重试 |

> **H5 对接要点**：`draw` 是**唯一的写接口**，且返回即代表事务已提交（`pending → paid → drawn`）。前端拿到响应后播开卡动画，动画结束跳结果页。

### 3.2 🔧 本期修改（1 条）· 💡 建议修改（2 条）

#### M1. `GET /user/home/feed` —— 增加 MySQL 降级通道 ✅ **已确认本期执行**

**现状问题**：该接口**完全依赖 Elasticsearch**，ES 不可用时直接 `500 search_unavailable`，**不做 MySQL 回退**（`service/user/home.go` 文件头注释明确写着「不 fallback 到 MySQL（spec 明确）」）。

这不只是 H5 的问题 —— **PC Web 首页同样会在 ES 抖动时白屏**，是当前线上的既存隐患。

**响应 200（裸 JSON）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `blind_boxes` | array | `{id, supplier_id, supplier_name, name, cover, price, promo_price?, rarity_summary, hot_score, created_at}` |
| `suppliers` | array | `{id, name, logo, blind_box_count, featured_rank}` |
| `fetched_at` | time | 数据时间 |

**已确认方案**（原方案 A）：`home/feed` 内部加 `ES 失败 → 降级查 MySQL` 兜底，响应结构与索引结果保持一致。改动小、对 H5 透明。

**降级设计要点**（完整契约见 openspec change `add-uni-h5-client` 的 `home-feed-fallback` 能力）：

| 维度 | 约定 |
|---|---|
| 触发条件 | ES 返回 error 或反序列化失败 → 降级；**ES 返回 0 条不降级**（0 条是合法业务结果） |
| DTO 同构 | 降级响应字段集合 MUST 与 ES 路径完全一致，客户端零分支 |
| `promo_price` | 尽力填充；无法确定 MUST 置 `null`，**禁止估算**（显示原价可接受，显示错价是资损） |
| 缓存回填 | 降级结果 MUST NOT 按正常 TTL 回填；不写或 TTL ≤ 30 秒 |
| 超时 | ES 查询短超时（800ms 量级），避免长时间阻塞 |
| 可观测 | WARN 日志 + 响应头 `X-Feed-Source: es \| mysql`，**MUST NOT 静默降级** |
| 双层失败 | MySQL 也失败才返回 500 `search_unavailable`（客户端无需新增分支） |

> **约束冲突提示**：既有 change `add-trading-card-blindbox-mvp` 的 spec 含「ES 不可用时不查 MySQL 兜底」。该约束被本次修订覆盖，其归档时需同步改表述（已列入任务 11.9）。

**改动范围**：`internal/service/user/home.go` 的 `loadFeed` 链路 + repository 层新增两条 MySQL 查询。全项目仅此一处后端改动。

### 3.3 ➕ 本期新增（前端 mock，后端契约在此定义）

> **重要说明**：以下 5 条接口**本期只在前端 mock 层实现**，后端不落地。
> 契约写在这里是为了：① 前端 mock 的返回结构从一开始就和未来后端一致，替换时零改动；② 后端实现可作为独立 change 后续接入。

现有后端登录是**「用户名 + 密码(bcrypt) + 点选验证码」**，与本方案的「手机号 + 短信码 + 滑块」**不是同一套机制**。因此这 5 条是**新增接口**，不动原有 `/user/login`（PC 端 Web 继续用）。

---

#### N1. POST `/user/sms/send` —— 发送短信验证码

- **鉴权**：无（公开）
- **限流**：**必须新增**（防刷）：同手机号 `1 次/60 秒`、`10 次/天`；同 IP `20 次/小时`
- **请求体**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `mobile` | string | ✅ | 中国大陆手机号，11 位，正则 `^1[3-9]\d{9}$` |
| `scene` | string | ✅ | 固定 `login`（预留 `bind` / `reset`） |

- **响应 200（信封）**：`{ code: "sms.ok", message: "sent", expires_in: 300 }`
- **错误**：`400 sms.invalid_mobile` / `429 sms.too_frequent` / `500 sms.internal`

**Mock 约定（本期前端）**：不真发短信；固定放行任意合法手机号，验证码固定为 **`000000`**；控制台打印 `[MOCK] sms code for 138xxxx = 000000`。

**后端落地约定（后续）**：`config/channel.yaml` 的 `sms` 渠道已是 `mock` driver，可直接复用；真实通道接入属独立 change。

---

#### N2. GET `/common/captcha/slider` —— 创建滑块验证码

- **鉴权**：无
- **响应 200**

| 字段 | 类型 | 说明 |
|---|---|---|
| `key` | string | 本次验证码唯一键，后续校验与登录都要带上 |
| `bg_image` | string | `data:image/png;base64,...` 背景图（含缺口） |
| `slider_image` | string | 滑块拼图块图 |
| `y` | int | 缺口纵坐标（固定，**横向拖动**） |
| `width` | int | 背景图宽 |
| `height` | int | 背景图高 |
| `expires_in` | int | 有效期秒数（建议 120） |

> **与现有点选验证码的关系**：现有 `click-captcha`（`GET /common/captcha/create`）是 **350×200 背景图 + 按序点击坐标** 的**点选**式，**不是滑块**。
> 滑块属**新增能力**，接口独立命名（`/common/captcha/slider*`），不复用 `/common/captcha/create`，避免与 admin 登录链路的点选契约互相干扰。

---

#### N3. POST `/common/captcha/slider/verify` —— 预检滑块（不消费 key）

- **鉴权**：无
- **请求体**：`{ key: string, x: int, w: int, h: int }`
  - `x`：滑块最终横向偏移；`w` / `h`：前端渲染尺寸（**校验时必须与创建时一致**）
- **响应 200**：`{ code: "captcha.ok", message: "verified" }`
- **错误**：`400 captcha.invalid_input` / `401 captcha.failed` / `410 captcha.expired`

**语义（对齐现有 click-captcha 契约）**：
- 本接口是**预检**，`deleteOnSuccess = false`，**不消费 key**，滑块可反复拖动直到通过。
- 真正的**消费型校验**发生在 `POST /user/login/mobile` 内部（`deleteOnSuccess = true`），**一次登录消费一次 key**。
- 容差：横向偏移误差建议 **±8px**（点选是 14px/24px，滑块需更严）。
- 同样适用 **per-key 答错计数**：连续失败 3 次 → 该 key 立即失效并强制刷新。

---

#### N4. POST `/user/login/mobile` —— 手机号登录（主接口）

- **鉴权**：无
- **限流**：建议 `login:{mobile}` **10 次/分钟**，防撞库
- **请求体**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `mobile` | string | ✅ | 手机号 |
| `sms_code` | string | ✅ | 6 位短信验证码 |
| `captcha_key` | string | ✅ | 滑块 key（来自 N2） |
| `captcha_x` | int | ✅ | 滑块横向偏移（服务端做**消费型**二次校验） |
| `remember` | bool | ❌ | 默认 false；true → token 30 天，false → 3 天 |

- **响应 200（裸 JSON，对齐现有 `/user/login` 结构）**

```json
{
  "user": {
    "id": 1,
    "username": "13800138000",
    "nickname": "用户8000",
    "avatar": "",
    "mobile": "13800138000",
    "balance": "1288.00",
    "status": 1,
    "last_login_at": "2026-10-14T17:20:00+08:00",
    "last_login_ip": "127.0.0.1"
  },
  "token": "0192f3a4-...."
}
```

> `balance` 是 **string**（后端 `%.2f` 格式化），不是 number —— 前端展示直接用，计算前需 `parseFloat`。

- **错误码**

| HTTP | code | 前端处理 |
|---|---|---|
| 400 | `login.invalid_input` | 参数异常 |
| 401 | `login.invalid_captcha` | **重置滑块**，提示「请重新完成验证」 |
| 401 | `login.invalid_sms_code` | 提示「验证码错误」，不重置滑块 |
| 403 | `login.account_disabled` | 提示账号被封禁 |
| 429 | `rate_limited` | 禁用按钮 3 秒 |
| 500 | `login.internal` | 通用失败 |

> **`login.invalid_credentials` 已移除**：在自动建号策略下「手机号未注册」不再是拒绝理由，该码无触发场景。系统 MUST NOT 以任何形式向客户端暴露注册状态。

- **新用户处理 ✅ 已确认**：
  - **首登自动建号**：`username` = 手机号，`password` 置空字符串，`balance` = 0，`status` = 1，同事务内完成建号与登录。

## 四、前端 Mock 方案

**已确认边界：mock 只覆盖 UI**（登录页交互及其配套接口），业务数据 100% 真实。

**统一开关**：`uni-h5/src/config/index.ts` 导出 `USE_MOCK = true`。

**分层**：`src/api/` 只做「URL + 参数 + 返回类型」，`src/mock/` 提供 `uni.request` 的拦截实现；切换真实接口时只改 `USE_MOCK`，业务代码零改动。

| Mock 接口 | 行为 | 性质 |
|---|---|---|
| `POST /user/sms/send` | 校验手机号正则；通过则返回成功，验证码固定 `000000`，`console.log` 打印 | 登录页 UI |
| `GET /common/captcha/slider` | 返回内置 base64 图 + 随机 `key`；**不校验真实缺口位置** | 登录页 UI |
| `POST /common/captcha/slider/verify` | **无条件返回通过**（直接滑到底即通过） | 登录页 UI |
| `POST /user/login/mobile` | 校验 `sms_code === '000000'`；通过则返回假 user（`balance` 固定 `1288.00`） | 登录页 UI |
| `GET /user/profile` | 返回登录时存的 user | 登录页 UI |

**其他业务接口（feed / detail / draw / orders）走真实后端**，保证主链路端到端真跑通。

**token 的处理（关键）**：mock 产出的 token 是假的，无法通过后端 `UserAuth()` 中间件。

已确认做法：**mock 只负责驱动登录页 UI 状态，token 走真接口**。登录页在 mock 校验通过后，后台静默调用真实的 `POST /user/login`（用户名 + 密码 + 点选验证码），用一个预置测试账号换取**真 token**，界面展示仍用 mock 的 user 数据。

这样做的收益：**抽卡会真实扣库存、真实产生订单**，`mall_draw_orders` 与 `mall_card_pool_items.stock` 都会真实变化 —— 链路验证价值远高于演示性质的假数据流。

**边界自检判据**：即便 `USE_MOCK` 被误开在生产环境，受影响的也**仅限于登录页交互**，商品与订单数据 MUST NOT 失真。已列入任务 4.9。

## 六、状态图 · 订单状态机

**数据来源**：`internal/domain/state/`，契约见 openspec `Draw order state machine`。

| 当前状态 | 合法目标状态 |
|---|---|
| `pending` | `paid`, `failed` |
| `paid` | `drawn`, `failed` |
| `drawn` | （终态） |
| `failed` | （终态） |

**关键约束**：
- 事务内推进 `pending → paid → drawn`，**任一步非法即整笔回滚**。
- 禁止跳级（`pending → drawn` 直接拒绝，返回 `ErrInvalidStateTransition`）。
- `drawn` / `failed` 是终态，任何转换都被拒。

**H5 展示映射**：

| 后端 status | H5 文案 | 色调 | 说明 |
|---|---|---|---|
| `pending` | 待支付 | 警示 | **正常抽卡链路几乎不会出现**（事务内瞬时态） |
| `paid` | 已支付 | 中性 | 事务已扣款，尚未出卡 |
| `drawn` | 已开卡 | 成功 | **正常终态**，可查看卡牌明细 |
| `failed` | 已失败 | 失败 | 终态，展示失败原因 |

> **H5 重要简化**：抽卡接口是**同步事务**，成功响应返回时订单已是 `drawn`。因此 H5 **不需要轮询订单状态**，也不存在「支付中」的中间态 UI。订单列表里看到的 `pending` / `paid` 只会是历史异常数据。

### 7.2 本期唯一的表改动（已确认执行）

```sql
-- 迁移 000017_users_register_source.up.sql
ALTER TABLE `users`
  ADD COLUMN `register_source` varchar(16) DEFAULT NULL
    COMMENT '注册来源(h5_mobile/admin/import等,NULL=未知)' AFTER `password`;
```

| 决策点 | 取值 | 理由 |
|---|---|---|
| 生成方式 | `migrate create users_register_source` | `db-migration` spec 要求新迁移 MUST 用 CLI 生成，**不允许手敲文件名** |
| 列位置 | `AFTER password`（表尾） | 不打扰既有列顺序与 ORM 字段假设，最小侵入 |
| 可空性 | `DEFAULT NULL`，不加 `NOT NULL` | 存量用户来源不可考，`NULL` 语义为「未知或历史数据」，比回填猜测值更诚实 |
| 存量回填 | **不做** | 回填属数据决策且无可靠判据 |
| 取值 | `h5_mobile` / `admin` / `import` | 长度留余量；不设 ENUM 或 CHECK，避免新增渠道时再改表 |
| 索引 | 暂不建 | 仅后台低频统计用；查询变频繁后再补 `idx_users_register_source` |
| down 回滚 | `DROP COLUMN register_source` | 结构可回滚，但已写入的来源值会丢失 |

**连带改动**：`internal/model/user.go` 新增 `RegisterSource *string`（`size:16`），与列名映射一致。

**边界（重要）**：本期只落**表结构 + model 字段**，**不含写入逻辑**。建号写 `h5_mobile` 依赖 `POST /user/login/mobile` 的服务端实现（后续 change）。本期结束时该列在所有库上都应为全 NULL —— 这是**预期状态，不是缺陷**。

**`mall_draw_order_items`**

`id` / `order_id` / `card_id` / `rarity`(varchar 8) / `snapshot_name`(varchar 100, NOT NULL) / `snapshot_image`(varchar 255) / 时间戳 / `deleted_at`
