# 开发工作流：codegraph + openspec + superpowers + ocr

> 2026-10-16 定稿。适用仓库：本仓（Go 后端 + `uni-h5` H5 客户端 + `web` 管理端）。
> 配套：`CLAUDE.md`「开发工作流」一节给出摘要；本文件是完整版。

---

## 0. 一页总览

四个工具**不是并列关系，而是各占开发流的一段，互不重叠**。串起来的关键不是「都装上」，
而是认清**每个工具的输出正好是下一个工具的输入**。

| 阶段 | 工具 | 产出物 | 可省？ |
|---|---|---|---|
| **S1 定位** | codegraph | 影响面清单（谁调用、谁受影响） | 小改动可省 |
| **S2 规划** | openspec | change（proposal / design / tasks + spec delta） | 纯重构可省 |
| **S3 执行** | superpowers / `tasks.md` | 代码 + 测试 | **不可省** |
| **S4 验证** | 编译单测 + ocr（限范围） | 通过 / 不通过 | **不可省** |
| **S5 收口** | `openspec archive` + git（+ `codegraph sync`） | specs 追平 + 索引新鲜 + 已提交 | **不可省** |

**核心不变量**（其余规则全由它推出）：

> `openspec/specs/` = 系统**当前真相**
> `openspec/changes/` = **待应用的补丁**
> `archive` = **唯一的应用动作**

真相过期比没有真相更危险 —— 你会拿着几天前的契约去改今天的代码。

## 1. 可用性矩阵

| 工具 | WorkBuddy | Claude Code | 形态 |
|---|---|---|---|
| **codegraph** | ✅（MCP 已接） | ✅ | CLI + MCP |
| **openspec** | ✅ | ✅ | CLI |
| **ocr** | ✅ | ✅ | CLI |
| **superpowers** | ❌ 用不上 | ✅（项目作用域） | Claude Code 插件 |
| ssf（spec-superflow） | 可运行 | 可运行 | CLI，**本项目不启用** |

superpowers 靠 Claude Code 的 **SessionStart hook** 注入其 skill —— Claude Code 专属机制，
**在 WorkBuddy 里完全不生效**。因此 **S3 的纪律层是可替换的**：
Claude Code 用插件；其他 agent 退化为「按 `tasks.md` 逐项执行 + 自写测试」。
**S1 / S2 / S4 / S5 四段跨 agent 完全一致。**

### 为什么不用 ssf

`ssf`（spec-superflow）的血缘（见其 `INSTALL.md`）：规划引擎来自 **Fission-AI/OpenSpec**、
执行纪律来自 **obra/superpowers** —— 它是两者的**合体**，不运行时依赖另两者。
不启用的三条理由：

1. **目录约定冲突**：ssf 用项目根 `changes/`，openspec 用 `openspec/changes/`。
2. **`ssf sync` ≡ `openspec archive`**：两套并存 = 两份真相。
3. **迁移成本 >> 收益**：本仓已有 24 个 capability（截至 2026-10-16）。

→ 处置：**当纪律手册读，不启用。**

## 2. 五个阶段

### S1 定位 —— codegraph

**何时用**：改动可能跨文件，或不确定某符号被谁依赖。
**何时跳过**：改函数内部逻辑、改文案、改样式。

```bash
codegraph explore "<英文符号名或英文关键词>"   # 首选
codegraph callers  <symbol>                  # 谁调用了它
codegraph impact   <symbol>                  # 改它会波及谁
codegraph affected <file>                    # 改这个文件会波及哪些测试
```

> ⚠️ **查询词用英文符号名，不要用中文自然语言** —— 索引走词法匹配，中文基本零命中。

**产出 → 下一阶段的接缝**：`impact` 的结果**直接成为** `proposal.md` 的影响面段。
这不是形式 —— 它决定 change 的范围是否划对了。

> ⚠️ **索引会过期**。判断：`codegraph status` 的索引时间 vs `git log -1 --format=%ci`。

### S2 规划 —— openspec

**何时用**：改动触及**契约面**（API、数据结构、用户可见行为）。
**何时跳过**：纯重构、依赖升级、格式化、纯文档 → 用 `--skip-specs` 或不进 openspec。

```bash
openspec list                       # 列 change
openspec validate <change>          # 必须过（warning 不阻断，见 S5）
```

**delta 的四条铁律**：

1. `changes/` 下的 delta 章节名**必须**是 `## ADDED / MODIFIED / REMOVED / RENAMED Requirements`；
   写成 `## Requirements` 会 **Abort**（`Delta parsing found no operations`）。
2. 每条 `### Requirement` **必须**带至少一个 `#### Scenario:`，否则 validate 拦下。
3. `MODIFIED` / `REMOVED` 引用的需求名**必须**在现行 `specs/` 中存在，否则归档 **Abort**。
4. 一个文件里出现**两个** `## ADDED Requirements` 章节是**安全的**，两个区块都会落库。

**实际做法**：动手前先 `grep -n "^### Requirement" specs/<capability>/spec.md` 读一遍现有
需求名，再决定写 ADDED 还是 MODIFIED —— 比事后靠工具报错试错快得多。

> ⚠️ **归档前必须逐条比对 delta 文本与代码现状**。别信「这个 change 是完成的，所以 delta 是对的」——
> 我们踩过：一个 change 标着 `✓ Complete`，其 delta 却写着「mock 开关**默认开启**」，
> 而代码早已改成默认关闭。归档会把与代码相反的文本**永久冻进 specs**。

**产出 → 下一阶段的接缝**：**`tasks.md` 本身就是 S3 的输入**。这是整条链上最实的一条缝，
不需要任何格式转换。

### S3 执行

**Claude Code**：`tasks.md` → `/superpowers:execute-plan`，TDD 铁律由插件强制。

**其他 agent（降级路径）**：

- 按 `tasks.md` 逐项做，**完成一项立即勾掉**（`- [x]`）—— 这是进度真相，别攒到最后补勾。
- **先写测试再写实现**；每条断言都要能回答「**如果实现坏了，这条断言会不会失败？**」

> 🔴 **本仓踩过的坑（务必遵守）**：`sqlmock` 下「守卫失效」**也会返回错误**
> （`call ... was not expected`）。所以 **`err != nil` 是弱断言** ——
> 余额守卫用例的初版就是这么写的，**负向对照照样通过**，完全锁不住回归。
> 正确做法：守卫返回**哨兵错误**，测试用 `errors.Is` 精确断言「是守卫拒绝的」。
>
> **通用规则：每写一条关键断言，就临时把实现改回旧写法跑一次（负向对照）。
> 如果测试依然通过，这条断言是假的。**

### S4 验证 —— 分级（含 token 纪律）

| 级别 | 内容 | 何时做 | 成本 |
|---|---|---|---|
| **L0 必做** | `go build` + `go vet` + `go test`；`vue-tsc --noEmit` + `eslint` + 构建 | **每次改动** | 低 |
| **L1 定向 ocr** | 仅对**改动文件**，**≤5 个** | 改动含并发 / 事务 / 边界 / 序列化语义 | 中 |
| **L2 全仓 ocr** | `ocr scan` | **禁止** | 极高 |

**L0 是主力手段，覆盖率远高于 ocr**：编译锁类型、单测锁行为、负向对照锁断言有效性。
实测：某轮真正有价值的 3 个问题**全部由 L0 + 人工复核发现**，不是 ocr。

**L1 的正确姿势**：

```bash
# 1. 先预览，确认文件数与范围（必做）
ocr review --path <file1>,<file2> --preview

# 2. 确认 ≤5 个文件后再真跑；不传 --effort（默认即可，high 会显著放大消耗）
ocr review --path <file1>,<file2> -b "<业务背景>" -f json -o <out.json> --timeout 10
```

**禁止事项**：

- ❌ 不带 `--path` 直接 `ocr review`（默认审查**全部**工作区改动）
- ❌ `ocr scan` 全仓扫描
- ❌ `--effort high` + 大文件集（实测 26 文件 / high → 12 分钟，消耗不可接受）
- ❌ 把 ocr 当验收主手段。**验收 = L0 全绿 + 关键路径的负向对照**

### S5 收口 —— 三步

```bash
# 1) 归档（应用 delta 到 specs，change 移入 archive/）
openspec archive <change> --yes

# 2) 索引同步 —— 仅当【代码】变了才需要；只改 spec 文件不影响 codegraph 索引
codegraph sync

# 3) 提交
git add -A && git commit
```

> 💡 **归档前自检**（`validate` 不查这个，缺了会在归档时 Abort）：

```bash
cd /d/aiproject
for d in openspec/changes/*/; do n=$(basename "$d"); [ "$n" = archive ] && continue
  for f in "$d"specs/*/spec.md; do
    cap=$(basename "$(dirname "$f")"); s="openspec/specs/$cap/spec.md"
    [ -f "$s" ] || continue
    awk '/^## /{sec=$0} /^### Requirement: /{if(sec~/MODIFIED|REMOVED|RENAMED/)print substr($0,18)}' "$f" \
      | while read -r r; do [ -n "$r" ] && grep -qF "### Requirement: $r" "$s" || echo "WILL ABORT: $n/$cap -> $r"; done
  done
done
```

## 3. 三条硬纪律

### 纪律一：完成即归档

不要攒。**积压的代价不是磁盘，是真相过期。** 2026-10-16 归档前：10 个 change 里
**7 个已完成却躺了 1~15 天**，导致 `specs/` 最新更新停在 10-11、`admin-login` 停在 09-27 ——
**读 specs 得到的是 5~19 天前的系统**。

### 纪律二：同一 capability，同一时刻只允许一个未归档 change 在改它

**唯一需要人来守的规则 —— 工具在这个盲区里完全不兜底**（隔离实验实测确证）：

> A、B 两个未归档 change 都 `MODIFIED` 同一需求名，A 先归档写入「并发安全」，
> B 后归档 —— 匹配只按 `### Requirement: <名>`、**不看内容**，
> 于是 A 的改动被 B 的原文**静默覆盖**：无警告、无冲突提示、两次都打印
> `Specs updated successfully`。

必须并行时：**后写的那个等前者归档后，重抄 base 文本再写 delta。**

**推论**：修复类改动**优先追加进已有未归档 change**，而不是新开一个。

### 纪律三：验证有 token 预算，ocr 默认不用

见 S4。一句话：**L0 是主力，ocr 是手术刀不是推土机。**

## 4. 完整走查示例

以「秒杀创建失败的回滚」修复为例：

```
S1  codegraph explore "seckill create rollback"
    → 定位 internal/service/supplier/seckill.go + internal/repository/mall/seckill_repository.go
S2  openspec：capability = trading-card-blindbox-mvp
    → 该 change 未归档，delta 追加进它（不新开 change，见纪律二）
    → 补完 delta 后 grep "### Requirement" 确认没有重名需求
S3  改代码 + 写测试
    → fakeSeckillRepo 加 Delete 计数；断言 deleteCalls==1 且 updateCalls==0
    → 负向对照：把实现改回 Update（旧写法）→ 用例必须失败
S4  L0：go build / vet / test 全绿
    L1：跳过 ocr（改动逻辑局部，已有单测覆盖）
S5  openspec validate → archive → codegraph sync（因为代码变了）→ git commit
```

## 6. 环境注意（本机 / 本仓特有）

- **Go 工具链需纯 ASCII 缓存路径**，否则 `go vet` / `go build` 可能被 SIGTERM 打断：
  ```bash
  export GOCACHE="C:/Users/Public/gocache" GOTMPDIR="C:/Users/Public/gotmp"
  ```
- **`gofmt -l` 在本仓不是有效门禁**：全仓约 183 个 Go 文件因 CRLF（`core.autocrlf=true`）
  被标记。判断自己改的代码格式：`tr -d '\r' < f.go > /tmp/x.go && gofmt -l /tmp/x.go`。
- **Vite 构建在沙箱下可能因批量删除保护失败**
  （`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，来自 `prepare-out-dir` 清空已存在的 outDir）。
  规避：**每次构建换一个全新的 `--outDir`**。
- **`vite.config.ts` 的 `server.proxy` 必须保留 `'/api': {...}` 这层上下文键**。丢掉后
  Vite 会把选项对象本身当 map 迭代，拿 `changeOrigin: true` 去建代理，报
  `TypeError: Cannot create property 'prependPath' on boolean 'true'`。
- **H5 开发令牌等变量只能放 `.env.development.local`**：`.env` 与 `.env.local`
  在 production 构建里**同样被加载**，令牌会明文内联进产物 JS。三道防线见
  `uni-h5/vite.config.ts`、`uni-h5/src/config/index.ts`、`uni-h5/scripts/verify-prod-bundle.mjs`。

## 7. 明确不做的事

- **不启用 ssf**（两份真相）
- **不做全仓 ocr**（token 不可接受，收益低于 L0）
- **不用 `ocr scan` 当验收**（验收 = L0 全绿 + 负向对照）
- **不在 `changes/` 里写 `## Requirements`**（必须用四个 delta 章节名）
- **不同时用两个未归档 change 改同一 capability**
- **不把纯重构 / 依赖升级塞进 openspec**（用 `--skip-specs`）
